# Domain Entities - Profile Update Service

## Overview

This document defines the domain entities and data structures for the profile update feature. These entities represent the core business objects and their relationships, independent of persistence technology.

---

## Entity Definitions

### Entity 1: User (Core Domain Entity)

**Purpose:** Represents a system user with identity, contact information, role, and access status.

#### Entity Identity
- **Entity Name:** User
- **Primary Key:** userId (Long)
- **Uniqueness Constraint:** email (globally unique)
- **Status:** Existing entity (enhancement required)

#### Attributes

| Attribute | Type | Nullable | Constraints | Purpose |
|-----------|------|----------|-----------|---------|
| userId | Long | NO | Primary key, auto-generated | Unique identifier |
| name | String | NO | Max 100 chars | Display name |
| email | String | NO | Valid email, unique | Unique identifier for login/contact |
| role | String | NO | Enum: ROLE_USER, ROLE_ADMIN | Authorization role |
| active | Boolean | NO | true/false | Account activation status |
| createdAt | Timestamp | NO | Immutable, auto-generated | Audit: creation timestamp |
| updatedAt | Timestamp | NO | Auto-updated | Audit: last modification timestamp |

#### Attribute Details

##### userId
- **Type:** Long (64-bit integer)
- **Constraints:** Primary key, NOT NULL, Auto-generated by database
- **Mutability:** Immutable
- **Purpose:** Unique identifier for the user
- **Example:** 1, 2, 100, 9999

##### name
- **Type:** String
- **Constraints:** NOT NULL, Max 100 characters
- **Mutability:** Mutable (updatable via profile update)
- **Purpose:** User's display name
- **Validation:** Not empty, alphanumeric + spaces/hyphens/apostrophes
- **Example:** "John Smith", "Mary-Jane O'Connor"

##### email
- **Type:** String
- **Constraints:** NOT NULL, Unique (across all users), Valid email format, Max 255 chars
- **Mutability:** Mutable (updatable via profile update)
- **Purpose:** Unique email identifier, authentication credential, contact address
- **Validation:** RFC 5322 email format
- **Storage:** Lowercase normalized
- **Example:** "john.smith@example.com", "user+tag@company.co.uk"

##### role
- **Type:** String (or Enum)
- **Constraints:** NOT NULL, Enum value
- **Mutability:** Mutable (updatable by admin only)
- **Purpose:** Authorization role determining user permissions
- **Valid Values:**
  - "ROLE_USER" - Standard user with basic permissions
  - "ROLE_ADMIN" - Administrator with full system permissions
- **Default:** "ROLE_USER" (for new users)
- **Example:** "ROLE_USER", "ROLE_ADMIN"

##### active
- **Type:** Boolean
- **Constraints:** NOT NULL, Default=true
- **Mutability:** Mutable (updatable by admin only)
- **Purpose:** Account activation/deactivation flag
- **Values:**
  - true = Account is active (user can authenticate)
  - false = Account is deactivated (user cannot authenticate)
- **Default:** true (accounts active by default)
- **Example:** true, false

##### createdAt (Audit Field)
- **Type:** Timestamp (Java: Instant, LocalDateTime, or ZonedDateTime)
- **Constraints:** NOT NULL, Immutable, Auto-generated
- **Mutability:** Immutable (set once at creation)
- **Purpose:** Record creation timestamp for audit trail
- **Format:** ISO 8601 (2024-01-15T10:30:00Z)
- **Example:** 2024-01-15T10:30:00Z

##### updatedAt (Audit Field)
- **Type:** Timestamp (Java: Instant, LocalDateTime, or ZonedDateTime)
- **Constraints:** NOT NULL, Auto-updated
- **Mutability:** Auto-updated (set at creation, updated on any modification)
- **Purpose:** Record last modification timestamp for audit trail
- **Format:** ISO 8601 (2024-01-15T10:30:00Z)
- **Example:** 2024-01-15T14:45:30Z (updated after profile update)

#### Entity Relationships
- User is the central entity in profile update feature
- No direct relationships to other entities in this feature (User stands alone)
- Foreign keys to User may exist from other domains (not relevant here)

#### Entity Lifecycle

```
1. Creation
   - userId: Auto-generated by database
   - name: Set during user creation
   - email: Set during user creation, must be unique
   - role: Set to ROLE_USER by default
   - active: Set to true by default
   - createdAt: Auto-set to current timestamp
   - updatedAt: Set to match createdAt

2. Updates (Profile Update)
   - userId: Cannot change (primary key)
   - name: Can be updated by self or admin
   - email: Can be updated by self or admin (must remain unique)
   - role: Can only be updated by admin
   - active: Can only be updated by admin
   - createdAt: Cannot change
   - updatedAt: Auto-updated to new timestamp

3. Deactivation (No deletion)
   - Instead of deletion: Set active=false
   - User record remains in database for audit/history
   - Deactivated user cannot authenticate
```

#### State Diagram

```
User Entity States
  │
  ├─ CREATED
  │  ├─ userId: Generated
  │  ├─ active: true (default)
  │  ├─ role: ROLE_USER (default)
  │  └─ Transition: Profile update
  │
  ├─ ACTIVE
  │  ├─ active: true
  │  ├─ User can authenticate and access system
  │  ├─ User can update own name/email
  │  ├─ Transitions:
  │  │  ├─ Admin can change role
  │  │  ├─ Admin can deactivate (set active=false)
  │  │  └─ Self can update name/email
  │
  ├─ ROLE_CHANGED
  │  ├─ role: Updated (ROLE_USER → ROLE_ADMIN or vice versa)
  │  ├─ Timestamp: updatedAt changes
  │  └─ Transitions: Any other update
  │
  └─ DEACTIVATED
     ├─ active: false
     ├─ User cannot authenticate
     ├─ Admin can reactivate (set active=true)
     └─ User record remains (not deleted)
```

#### Business Rules Applied to Entity
- **BR1-2:** Name and email stored in User entity
- **BR5:** Role stored as enum in User entity
- **BR6:** Active status stored as boolean flag
- **BR8:** User ID is immutable primary key
- **BR10:** Email must be unique across all User records
- **BR11:** Only valid role values stored

#### Entity Constraints

```sql
-- Primary key constraint
CONSTRAINT PK_USER PRIMARY KEY (userId)

-- Unique constraint on email
CONSTRAINT UQ_USER_EMAIL UNIQUE (email)

-- Not null constraints
CONSTRAINT NN_USER_NAME NOT NULL (name)
CONSTRAINT NN_USER_EMAIL NOT NULL (email)
CONSTRAINT NN_USER_ROLE NOT NULL (role)
CONSTRAINT NN_USER_ACTIVE NOT NULL (active)

-- Check constraint on role (if supported by DB)
CONSTRAINT CK_USER_ROLE CHECK (role IN ('ROLE_USER', 'ROLE_ADMIN'))

-- Check constraint on active
CONSTRAINT CK_USER_ACTIVE CHECK (active IN (true, false))
```

## Data Transfer Objects (DTOs)

### DTO 1: UpdateUserRequest (Request DTO)

**Purpose:** Encapsulate profile update request data from client, with request-level validation

**Scope:** Request payload only (input)

**Mutability:** Mutable (created per request)

**Validation:** Field-level via Jakarta Bean Validation annotations

#### DTO Attributes

| Attribute | Type | Nullable | Validation | Purpose |
|-----------|------|----------|-----------|---------|
| name | String | YES | @NotEmpty, @Size(max=100) | Updated display name |
| email | String | YES | @Email, @NotEmpty | Updated email address |
| role | String | YES | @ValidRole or enum check | Updated role (admin only) |
| active | Boolean | YES | (boolean validation) | Updated active status (admin only) |

#### Attribute Details

##### name
- **Type:** String
- **Nullable:** YES (null means don't update)
- **Validation Annotations:**
  - `@NotEmpty` - If provided, must not be empty
  - `@Size(max = 100)` - If provided, max 100 characters
- **Purpose:** Optional update to display name
- **Example:** "New Name", null

##### email
- **Type:** String
- **Nullable:** YES (null means don't update)
- **Validation Annotations:**
  - `@Email` - If provided, must be valid email format
  - `@NotEmpty` - If provided, must not be empty
- **Purpose:** Optional update to email address
- **Example:** "newemail@example.com", null

##### role
- **Type:** String
- **Nullable:** YES (null means don't update)
- **Validation Annotations:**
  - Custom `@ValidRole` or enum validation
  - Must be one of: "ROLE_USER", "ROLE_ADMIN"
- **Purpose:** Optional role update (admin only in authorization)
- **Example:** "ROLE_ADMIN", "ROLE_USER", null

##### active
- **Type:** Boolean
- **Nullable:** YES (null means don't update)
- **Validation Annotations:**
  - Standard boolean validation (Spring handles)
- **Purpose:** Optional active status update (admin only)
- **Example:** true, false, null

#### DTO Validation Behavior

```
Validation Scope: REQUEST level (DTO deserialization)

Field: name
  IF name is provided (not null):
    - Apply @NotEmpty validation
    - Apply @Size(max=100) validation
    - Return 400 if validation fails
  ELSE:
    - Skip field validation (partial update)

Field: email
  IF email is provided (not null):
    - Apply @Email validation
    - Apply @NotEmpty validation
    - Return 400 if validation fails
  ELSE:
    - Skip field validation (partial update)

Field: role
  IF role is provided (not null):
    - Apply enum/range validation
    - Return 400 if invalid value
  ELSE:
    - Skip field validation (partial update)

Field: active
  IF active is provided (not null):
    - Verify boolean type
    - Return 400 if not boolean
  ELSE:
    - Skip field validation (partial update)
```

#### Example Payloads

**Full Update:**
```json
{
  "name": "John Smith",
  "email": "john@example.com",
  "role": "ROLE_ADMIN",
  "active": true
}
```

**Partial Update (Email Only):**
```json
{
  "name": null,
  "email": "newemail@example.com",
  "role": null,
  "active": null
}
```

**Minimal Update (Name Only):**
```json
{
  "name": "New Name"
}
```

#### DTO Validation Error Response

```json
HTTP 400 Bad Request
{
  "timestamp": "2024-01-15T10:30:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "details": [
    {
      "field": "email",
      "message": "must be a valid email address",
      "rejectedValue": "invalid-email"
    },
    {
      "field": "name",
      "message": "size must be between 1 and 100",
      "rejectedValue": "A" * 101
    }
  ]
}
```

### DTO 2: UserResponse (Response DTO)

**Purpose:** Return updated user profile information to client after successful update

**Scope:** Response payload only (output)

**Mutability:** Immutable after creation (read-only response)

#### DTO Attributes

| Attribute | Type | Nullable | Purpose |
|-----------|------|----------|---------|
| id | Long | NO | User's unique identifier |
| name | String | NO | User's display name |
| email | String | NO | User's email address |
| role | String | NO | User's role |
| active | Boolean | NO | User's active status |

#### Attribute Details

##### id
- **Type:** Long
- **Nullable:** NO
- **Purpose:** User's unique identifier
- **Source:** User.userId
- **Example:** 1, 100, 9999

##### name
- **Type:** String
- **Nullable:** NO
- **Purpose:** User's display name
- **Source:** User.name
- **Example:** "John Smith"

##### email
- **Type:** String
- **Nullable:** NO
- **Purpose:** User's email address
- **Source:** User.email
- **Example:** "john@example.com"

##### role
- **Type:** String
- **Nullable:** NO
- **Purpose:** User's authorization role
- **Source:** User.role
- **Example:** "ROLE_USER", "ROLE_ADMIN"

##### active
- **Type:** Boolean
- **Nullable:** NO
- **Purpose:** User's active status
- **Source:** User.active
- **Example:** true, false

#### Response DTO Creation Flow

```
1. User entity updated in database
2. Service layer retrieves updated entity
3. Convert User entity → UserResponse DTO
   - id: user.getId()
   - name: user.getName()
   - email: user.getEmail()
   - role: user.getRole()
   - active: user.getActive()
4. Return as response body
```

#### Example Successful Response

```json
HTTP 200 OK
{
  "id": 1,
  "name": "John Smith",
  "email": "john.smith@example.com",
  "role": "ROLE_USER",
  "active": true
}
```

## Authentication Principal

### Principal Entity

**Purpose:** Represents the authenticated user extracted from security context

#### Principal Attributes

| Attribute | Type | Source | Purpose |
|-----------|------|--------|---------|
| userId | Long | UserDetailsService principal | Authenticated user's ID |
| username | String | UserDetailsService | Authenticated user's username (email) |
| authorities | Collection<String> | UserDetailsService | User's roles/authorities |
| isAuthenticated | Boolean | Spring Security | Authentication status |

#### Principal Extraction Pattern

```
Spring SecurityContext
  ├─ Authentication object
  │  ├─ Principal (UserDetails)
  │  │  ├─ username: email address
  │  │  ├─ authorities: [ROLE_USER, ROLE_ADMIN, ...]
  │  │  └─ (custom userId field)
  │  │
  │  └─ isAuthenticated(): true/false
```

#### Principal Usage in Profile Update

```
1. Extract from SecurityContextHolder
   Authentication auth = SecurityContextHolder.getContext()
     .getAuthentication()

2. Get authenticated user ID
   Long authenticatedUserId = (Long) auth.getPrincipal()
   // or: auth.getName() for username

3. Get user roles
   Collection<String> roles = auth.getAuthorities()

4. Check if admin
   boolean isAdmin = roles.contains("ROLE_ADMIN")

5. Pass to service
   userService.updateUser(
     targetUserId, 
     request, 
     authenticatedUserId, 
     isAdmin
   )
```

## Data Validation Hierarchy

```
Validation Layers (Bottom to Top)

Layer 4: BUSINESS RULES VALIDATION (Service)
         ├─ Email uniqueness (query DB)
         ├─ Role validity (against defined roles)
         ├─ User existence (user lookup)
         └─ Authorization (based on authentication principal)

Layer 3: BUSINESS LOGIC VALIDATION (Service)
         ├─ Field restrictions (which fields can be updated)
         ├─ Partial update handling (null checks)
         └─ State management

Layer 2: DTO/FORM VALIDATION (Spring Validation)
         ├─ @Email on email field
         ├─ @Size(max=100) on name field
         ├─ @NotEmpty on non-null fields
         └─ Field-level constraints

Layer 1: REQUEST/BINDING VALIDATION (Spring)
         ├─ JSON deserialization
         ├─ Type coercion
         └─ Syntax validation
```

## Data Flow Through Entities/DTOs

```
1. Client sends JSON request
   ↓
   {
     "name": "New Name",
     "email": "new@ex.com",
     "role": null,
     "active": null
   }

2. Spring deserializes JSON → UpdateUserRequest DTO
   ↓
   UpdateUserRequest {
     name = "New Name"
     email = "new@ex.com"
     role = null
     active = null
   }

3. DTO validation applies
   ↓
   @Size(max=100) validated for name
   @Email validated for email
   Partial update (nulls allowed)

4. Service receives DTO and authenticated principal
   ↓
   updateUser(userId=1, request, authUserId=1)

5. Service authorization checks
   ↓
   Are you authorized to update these fields?
   (Business logic validation)

6. Service loads User entity
   ↓
   User {
     userId = 1
     name = "Old Name"
     email = "old@ex.com"
     role = "ROLE_USER"
     active = true
   }

7. Service maps DTO to entity
   ↓
   user.setName("New Name")
   user.setEmail("new@ex.com")
   user.setUpdatedAt(now)

8. Service persists entity
   ↓
   User {
     userId = 1
     name = "New Name"
     email = "new@ex.com"
     role = "ROLE_USER"
     active = true
     updatedAt = 2024-01-15T10:45:00Z
   }

9. Service maps entity to UserResponse
   ↓
   UserResponse {
     id = 1
     name = "New Name"
     email = "new@ex.com"
     role = "ROLE_USER"
     active = true
   }

10. Spring serializes UserResponse → JSON
    ↓
    {
      "id": 1,
      "name": "New Name",
      "email": "new@ex.com",
      "role": "ROLE_USER",
      "active": true
    }

11. Client receives JSON response
```

## Summary

**Domain Entities:**
- **User Entity:** Core domain object with 5 main fields + 2 audit fields
  - userId (PK), name, email (unique), role (enum), active (boolean)
  - Plus: createdAt, updatedAt (audit)

**DTOs:**
- **UpdateUserRequest:** Request payload with optional fields (partial updates)
- **UserResponse:** Response payload with complete user profile

**Authentication:**
- **Principal:** Extracted from Spring Security, contains userId and roles

**Validation:**
- **4 layers:** Request binding → DTO validation → Business logic → Business rules

**Constraints:**
- **Entity-level:** Primary key, unique email, not-null fields, enum roles
- **DTO-level:** Size limits, email format, field validation
- **Service-level:** Email uniqueness checks, authorization, business rules

This design ensures data consistency, validation at appropriate layers, and clear separation between entity, DTO, and authentication representations.
